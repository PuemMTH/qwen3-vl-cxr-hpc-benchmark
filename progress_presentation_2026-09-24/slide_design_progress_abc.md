## Slide 2 — คำถามจากครั้งก่อน

### ข้อความบนหน้า

**ครั้งก่อนเราต้องการคำตอบ 3 เรื่อง**

`Capacity = รันรุ่นใหญ่ · Throughput = ภาพต่อชั่วโมง · Quality = ความถูกต้อง`

1. **Capacity** — A100 รันโมเดลขนาดใหญ่ (8B) ที่ RTX 5070 โหลดไม่ไหวได้หรือไม่
2. **Throughput** — ส่งภาพหลายใบพร้อมกันหรือเพิ่ม GPU แล้วประมวลผลภาพได้มากขึ้นเท่าไร
3. **Quality** — ตอบตรงคำตอบอ้างอิงมากขึ้นหรือไม่ และเมื่อใช้โมเดลกับพรอมป์เดียวกันบนสองเครื่อง ผลรายภาพตรงกันหรือไม่

แถบข้อความท้ายหน้า: `A = เทียบเครื่อง · B = ความถูกต้อง · C = ส่งหลายภาพพร้อมกัน / หลาย GPU`

### การจัดวาง

หัวข้อด้านบน แล้วเรียง 3 คำถามเป็น 3 บรรทัดใหญ่จากบนลงล่าง ตัวอักษรคำหลักหนากว่าคำอธิบาย ใช้สีน้ำเงินกับ Capacity สีส้มกับ Throughput และสีแดงกับ Quality ให้ตรงกับหน้าสรุป

### ภาพ/กราฟที่จะใส่ทีหลัง

ผังบาง ๆ เชื่อม `Capacity / Throughput / Quality` เข้ากับ `A / B / C` เพื่อพาผู้ฟังจากแผนเดิมไปผลใหม่ ไม่มีตัวเลขในภาพนี้

### คำพูดประกอบ

“สามข้อนี้มาจาก Need และแผนทดลองใน slide ครั้งก่อน รอบนั้นมี local pilot 20 ภาพ แต่ยังไม่มีผล A100 ระดับชุดข้อมูล”

## Slide 4 — Batch คือส่งหลายภาพพร้อมกัน

### ข้อความบนหน้า

**Batch 4 = 4 คู่ภาพ–พรอมป์ (prompt) · คลาสไม่ต้องเหมือนกัน · ตอบแยกรายภาพ**

`ภาพ 1 + พรอมป์เดียวกัน` `ภาพ 2 + พรอมป์เดียวกัน` `ภาพ 3 + พรอมป์เดียวกัน` `ภาพ 4 + พรอมป์เดียวกัน` → `โมเดลสร้างคำตอบ 1 ครั้ง` → `ผลทำนายแยก 4 รายการ`

**เหตุผลที่เพิ่ม batch:** แต่ละภาพมีพรอมป์ของตัวเองที่ใช้ข้อความเดียวกัน; เมื่อนำหลายคู่เข้าประมวลผลพร้อมกัน จะลดจำนวนครั้งที่เรียกโมเดลต่อ 1,000 ภาพ: batch 1 = 1,000 ครั้ง; batch 2 = 500 ครั้ง; batch 4 = 250 ครั้ง; batch 8 = 125 ครั้ง (ไม่รวม warm-up)

**สิ่งที่วัดเพื่อเลือก batch:** ภาพต่อชั่วโมง เวลาต่อ batch และหน่วยความจำ GPU; ไม่สมมติว่าภาพต่อชั่วโมงต้องเพิ่มตามจำนวนภาพต่อ batch แบบเส้นตรง

**คลาสใน batch:** โค้ด inference อ่าน `blind_manifest.csv` ที่ไม่มี `true_label` แล้วนำภาพที่อยู่ติดกันในไฟล์มาจัด batch จึงไม่ได้บังคับว่าคลาสต้องเหมือนกันหรือคละกัน สำเนา `performance-1000` ใน workspace มี NORMAL 500 และ PNEUMONIA 500 ภาพ; เมื่อตรวจร่วมกับ `labels.csv` พบว่า batch 2 ทั้ง 500 ชุดเป็นคลาสเดียวกัน, batch 4 คละคลาส 2 จาก 250 ชุด, batch 8 คละคลาส 2 จาก 125 ชุด เพราะลำดับ `image_id` ที่เรียงไว้ ผลนี้เป็นการตรวจสำเนา manifest ใน workspace ไม่ใช่ข้อกำหนดของการทำ batch

### การจัดวาง

กล่องภาพสี่กล่องอยู่แถวบน ลูกศรลงไปที่กล่องการเรียกโมเดลหนึ่งครั้ง แล้วลงไปที่กล่องผลลัพธ์แยกสี่รายการ ใช้สีฟ้ากับภาพ สีส้มกับ `generate` ตามภาษาภาพของกราฟ A/C

### คำพูดประกอบ

“Batch 1 คือหนึ่งคู่ (ภาพ 1 + พรอมป์ P) ส่วน batch 2 คือสองคู่ (ภาพ 1 + พรอมป์ P) และ (ภาพ 2 + พรอมป์ P) ที่ประมวลผลพร้อมกัน ข้อความ P เหมือนกัน แต่ภาพและคำตอบแยกกัน ภาพทั้งสองไม่จำเป็นต้องเป็นคลาสเดียวกัน เราจึงเพิ่ม batch เพื่อทดสอบว่าการลดจำนวนครั้งที่เรียกโมเดลช่วยให้ได้ภาพต่อชั่วโมงมากขึ้นเท่าไร พร้อมดูเวลาต่อ batch และหน่วยความจำ GPU”

**อ้างอิง:** [โค้ดการจัด batch](../ai-for-research/module-06-vlm/vlm-cxr-benchmark/vlm_cxr/inference.py), [รายงาน §4](evidence/report_abc.md)

## Slide 7 — ตารางเวลาที่วัดในงานทดลอง

### ข้อความบนหน้า

**เวลาที่ใช้เทียบความเร็ว A/C = ผลรวม `pipeline_seconds` ของ batch ที่สำเร็จหลัง warm-up**

| เวลาที่วัด | เริ่ม → จบ | การใช้ |
|---|---|---|
| โหลดโมเดล (`model_loading_seconds`) | เริ่มโหลดโมเดลและ processor → พร้อมใช้งาน | โค้ดวัด; แยกจาก pipeline |
| สร้างคำตอบ (`generation_seconds`) | ก่อน `model.generate` → GPU สร้างคำตอบเสร็จ | โค้ดวัด; เป็นส่วนหนึ่งของ pipeline |
| อ่านภาพจนได้คำตอบ (`pipeline_seconds`) | ก่อนเปิดภาพจากดิสก์ → หลัง decode/parse คำตอบ | โค้ดวัด; ใช้คำนวณผล A/C |
| รันหนึ่งรอบ (`elapsed_seconds`) | เริ่ม subprocess → process จบ ใน A/B/C1 | วัดแยก; ไม่ใช้คิดความเร็ว |
| รันหลาย GPU (`wall_seconds`) | launcher เริ่ม rank → ทุก rank จบ ใน C2 | วัดแยก; ไม่ใช้คิดความเร็ว |
| รอคิว LANTA (`Queue wait`) | ส่งงาน SLURM → เริ่มได้รับ GPU | เวลา scheduler; รายงานแยก |
| ใช้ GPU บน LANTA (`Allocation elapsed`) | เริ่มได้รับ GPU → คืน GPU | เวลา scheduler; รายงานแยก |

กรอบสีน้ำเงินใต้ตาราง: `ใช้ประเมินความเร็ว A/C: รวม pipeline ของ batch สำเร็จหลัง warm-up; ไม่รวมโหลดโมเดลหรือรอคิว`  
`ช่วงที่จับ: ก่อนเปิดภาพ → อ่าน/ปรับภาพ → เตรียมภาพ+พรอมป์และส่งเข้า GPU → generate → decode/parse คำตอบ`  
`C2 ใช้ GPU ที่ช้าที่สุดต่อรอบ แล้วหามัธยฐาน 5 รอบ · B วัดความถูกต้องจากคำทำนาย ไม่ใช้เวลา`

เวลาในไฟล์ผลจากโค้ดเป็นวินาที `[s]`; ตาราง scheduler บางแห่งแสดง `นาที:วินาที` และแปลงเป็นวินาทีได้ `generation_seconds` อยู่ภายใน `pipeline_seconds` จึงห้ามบวกสองค่านี้เข้าด้วยกัน ไม่มีเวลาที่จับแยกสำหรับอ่านภาพ เตรียม tensor ส่งข้อมูลเข้า GPU หรือ decode/parse

ที่มา: [นิยามเวลาจากโค้ดและไฟล์ผล](evidence/timing_scope.md), [เวลารอคิวและใช้ GPU จาก SLURM](evidence/resource_abc.md). `generation_seconds_total`, `pipeline_seconds_total`, p50/p95 และเวลาเฉลี่ยต่อภาพเป็นค่าที่สรุปจากเวลาที่จับ ไม่ใช่ตัวจับเวลาใหม่

### การจัดวาง

ตาราง 7 แถวเต็มหน้า ใช้พื้นสีอ่อนเน้นแถว `pipeline_seconds`; ส่วนหัวอธิบายว่าเป็นเวลาที่ใช้เทียบความเร็ว ส่วน 2 แถวสุดท้ายเป็นเวลา SLURM แยกจากเวลาที่โค้ดวัด กรอบสีน้ำเงินใต้ตารางแจกแจงขั้นตอนที่อยู่ในเวลาประเมินและแยกการวัดความถูกต้อง B ออกให้ชัด

### ภาพ/กราฟ

ไม่มีภาพ ใช้ตารางพร้อมเส้นแบ่งและแถบสีน้ำเงินที่แถวเวลาที่นำไปคำนวณ

### คำพูดประกอบ

“เราวัดเวลาไว้หลายขอบเขต ผลความเร็ว A และ C ใช้เวลา pipeline ที่เริ่มก่อนเปิดไฟล์ภาพ ครอบคลุมการอ่านและปรับภาพ เตรียมภาพกับพรอมป์ ส่งเข้า GPU สร้างคำตอบ และอ่านผลจน parse เสร็จ แล้วรวมเฉพาะ batch ที่สำเร็จหลัง warm-up สำหรับ C2 ใช้เวลาของ GPU ที่ช้าที่สุดต่อรอบแล้วหามัธยฐาน 5 รอบ ส่วนเวลาโหลดโมเดลและรอคิวไม่ได้อยู่ในตัวเลขนี้ คะแนนความถูกต้อง B มาจากคำทำนายเทียบคำตอบอ้างอิง ไม่ได้ใช้เวลา”

## Slide 9 — Experiment A: ความเร็วต่อ GPU

### ข้อความบนหน้า

**RTX 5070 ใช้เวลาประมวลผลภาพ (pipeline) น้อยกว่า A100 ทั้ง 3 แบบที่ทดสอบ**

| โมเดล | RTX เวลาประมวลผล [s] | A100 เวลาประมวลผล [s] | A100 เทียบ RTX [×] |
|---|---:|---:|---:|
| 2B BF16 | 175.632 | 269.218 | **0.652** |
| 4B BF16 | 231.581 | 329.219 | **0.703** |
| 8B NF4 | 337.121 | 428.675 | **0.786** |

ข้อความใต้ตาราง: `เวลาในตาราง = รอบที่ให้อัตราส่วนค่ากลาง: 2B/4B รอบ 3 · 8B รอบ 5` จึงไม่ใช่มัธยฐานเวลาของแต่ละเครื่องแยกกัน

บรรทัดกำกับ: `1 GPU · batch 1 · 1,000 ภาพไม่ซ้ำ (859 ผู้ป่วย) · ใช้ภาพชุดเดิมซ้ำ 5 รอบ`  
**กรอบนิยามเวลาที่ต้องเห็นบนหน้า (วางติดกับตาราง/สมการ):**

**เวลา pipeline [s] = เริ่มจับก่อนเปิดภาพจากดิสก์ และจบหลัง decode/parse คำตอบเสร็จในแต่ละ batch**; ค่าที่แสดงในตารางเป็นผลรวมเวลา batch ที่สำเร็จหลัง warm-up ของรอบที่ให้อัตราส่วนค่ากลาง

| เวลาที่วัด | ใช้คิดอัตราส่วน A100 เทียบ RTX หรือไม่ | ขอบเขต |
|---|---|---|
| **Pipeline total [s]** | **ใช้** | รวม batch ที่สำเร็จหลัง warm-up: อ่าน/ย่อภาพ → เตรียม tensor+ส่งเข้า GPU → generate → decode/parse |
| Model load / round wall / queue | ไม่ใช้ | เป็นเวลาคนละขอบเขต |

`Generation` เป็นส่วนหนึ่งของ pipeline แต่ไม่ได้ใช้เดี่ยว ๆ เป็นตัวหารของอัตราส่วน  
ที่มาของเวลาในตาราง: จับ `pipeline_seconds` ตั้งแต่ก่อนเปิดภาพจน decode/parse คำตอบเสร็จในแต่ละ batch; รวมเฉพาะ batch ที่สำเร็จหลัง warm-up เป็น `pipeline_seconds_total` ของรอบนั้น แล้วจับคู่รอบเดียวกันระหว่างสองแพลตฟอร์ม ตารางแสดง **รอบที่ให้อัตราส่วนค่ากลาง** จาก 5 รอบ จึงไม่ใช่ตารางเวลามัธยฐานของแต่ละเครื่องแยกกัน

| ตัวอย่าง 4B BF16 รอบ 3 | Generation [s] | ส่วนอื่นใน pipeline [s] | Pipeline total [s] |
|---|---:|---:|---:|
| RTX 5070 | 212.803 | 18.778 | **231.581** |
| A100 | 304.437 | 24.782 | **329.219** |

`ส่วนอื่นใน pipeline = pipeline total − generation` ครอบคลุมการอ่าน/ปรับภาพ เตรียม tensor/ส่งเข้า GPU และ decode/parse รวมกัน ข้อมูลชุดนี้ **ไม่ได้จับเวลาแยก** แต่ละขั้น จึงแจกแจงเป็นวินาทีรายขั้นไม่ได้

สมการบนหน้า (อัตราส่วนไม่มีหน่วย; รายงานเป็น `×`):

$$
S_A=\operatorname{median}_{r=1,\ldots,5}
\left(\frac{t_{\mathrm{RTX},r}\;[\mathrm{s}]}{t_{\mathrm{A100},r}\;[\mathrm{s}]}\right)
$$

นิยามในสมการ: `t_{platform,r} = ผลรวม pipeline time [s] ของ batch ที่สำเร็จหลัง warm-up ในรอบ r`  
ข้อจำกัดบนหน้า: `Python/PyTorch/CUDA ต่างเวอร์ชัน จึงเทียบแพลตฟอร์ม ไม่ได้แยกผลจากตัว GPU`

### การจัดวาง

ข้อสรุปอยู่บนสุด ตารางอยู่กลางหน้า กรอบนิยามเวลาติดใต้ตารางและอยู่ก่อนสมการ ส่วนข้อจำกัดอยู่ท้ายหน้า สีของคอลัมน์ Local/A100 คงตามสีกลางของ deck; เน้นคำว่า `ใช้` และคอลัมน์ pipeline ด้วยสีเดียวกัน

### ภาพ/กราฟที่จะใส่ทีหลัง

กราฟแท่งแนวนอน 3 แถวของ `A100 เทียบ RTX` พร้อมเส้นอ้างอิง `1.0×` ทั้งสามแท่งหยุดก่อนเส้น ภาพนี้ต้องทำให้เห็นว่า “ต่ำกว่า 1” โดยไม่ต้องอ่านตัวเลขละเอียด

### คำพูดประกอบ

“ผลนี้ไม่สนับสนุนสมมติฐานว่า A100 เร็วกว่าในงาน batch 1 ขนาด 2B–8B ที่โหลดบน local ได้ แต่ยังไม่สรุปว่า GPU A100 ช้ากว่าโดยตัวมันเอง เพราะ software stack สองเครื่องต่างกัน”

ตัวอย่างคำตอบหากถามที่มาค่า: 4B รอบที่ 3 ใช้ pipeline `231.581 s` บน RTX 5070 และ `329.219 s` บน A100 ได้ `(231.581 s) ÷ (329.219 s) = 0.7034×`; รายงานใช้อัตราส่วนรายรอบทั้ง 5 รอบแล้วหามัธยฐาน ไม่ใช่หารเวลามัธยฐานของสองเครื่องแยกกัน ตารางเลือกแสดงรอบที่ให้ค่ากลางของอัตราส่วนเพื่อให้ตรวจสูตรได้ตรง

คำว่า `image-equivalents` ในรายงานต้นทางหมายถึงจำนวนรายการภาพที่ประมวลผลต่อรอบ สำหรับ Experiment A นี้ manifest มี image ID, path และ SHA-256 ไม่ซ้ำครบ 1,000 รายการ จึงใช้คำว่า “1,000 ภาพไม่ซ้ำ” บน slide ให้ชัดกว่า; การรัน 5 รอบใช้ภาพชุดเดิมซ้ำ ไม่ได้เพิ่มจำนวนภาพเฉพาะเป็น 5,000 ภาพ

**อ้างอิง:** [รายงาน §2](evidence/report_abc.md), [systems summary](evidence/systems-summary.json), [ขอบเขตเวลา pipeline](evidence/timing_scope.md)

**A100 เพิ่มปริมาณงานได้เมื่อส่งภาพเป็น batch และแบ่งงานหลาย GPU**

**C1 · A100 1 ใบ · 4B BF16 · 1,000 ภาพ**  
Batch `1 / 2 / 4 / 8` → `10,894 / 17,476 / 27,541 / 41,614 ภาพ/ชม.`  
Batch 8 = `(41,614 ภาพ/ชม.) ÷ (10,894 ภาพ/ชม.) = 3.82×` ของ batch 1 (**throughput ratio**)

ตัวหารของ throughput บนหน้า: `Pipeline total [s] = ผลรวมเวลา batch ที่สำเร็จหลัง warm-up`; `ภาพ/ชม. = 3,600 × จำนวนภาพ ÷ Pipeline total [s]` (หาค่ารายรอบแล้วรายงานมัธยฐาน 5 รอบ)

**C2 · 4B BF16 · batch 8 · งานคงที่ 2,000 ภาพ**  

| GPU | เวลา pipeline มัธยฐาน [s] | เร็วขึ้น [×] |
|---:|---:|---:|
| 1 | 176.549 | 1.000 |
| 2 | 88.691 | 1.991 |
| 4 | 45.105 | 3.914 |

**กรอบนิยามเวลาที่ต้องเห็นบนหน้า (วางติดกับตาราง/สมการ C2):**  
`เวลาที่ใช้คิดว่าเร็วขึ้นเท่าไร = Pipeline total [s] ต่อ rank: อ่าน/ย่อภาพ → เตรียม tensor+ส่งเข้า GPU → generate → decode/parse; รวมเฉพาะ batch ที่สำเร็จหลัง warm-up`  
`ต่อรอบใช้ rank ที่ช้าที่สุด → หามัธยฐาน 5 รอบ`  
`Model load / complete-round wall / queue วัดแยก แต่ไม่ใช้คิดอัตราส่วน`

ประสิทธิภาพเมื่อเพิ่ม GPU = `(เร็วขึ้นกี่เท่า ÷ จำนวน GPU) × 100`; ที่ 2/4 GPU ได้ `99.53% / 97.86%`

สมการใต้ข้อมูล C2 (อัตราส่วนไม่มีหน่วย; รายงานเป็น `×`):

$$
T_k=\operatorname{median}_{r=1,\ldots,5}\left(\max_j\sum_b t_{\mathrm{pipeline},b,j,r}\;[\mathrm{s}]\right),
\qquad S_{C2}(k)=\frac{T_1}{T_k}
$$

### การจัดวาง

แบ่งหน้าซ้ายขวาเท่า ๆ กัน: ซ้าย C1, ขวา C2 แต่ละส่วนมีชื่อ workload ของตัวเอง คั่นด้วยเส้นบางเพื่อไม่ให้คนอ่านนำเลข throughput ของ C1 ไปเทียบกับ C2 เพิ่มแท่งสั้นในแถว C1 ตามภาพต่อชั่วโมง (แท่งยาวขึ้น) และในแถว C2 ตามเวลา pipeline (แท่งสั้นลง) โดยคงตัวเลขและหน่วยกำกับไว้ วางกรอบนิยาม pipeline สีอ่อนใต้ตาราง C2

### ภาพ/กราฟที่จะใส่ทีหลัง

- ฝั่งซ้าย: กราฟแท่ง throughput ตาม batch 1, 2, 4, 8 โดย batch 8 สูงสุด
- ฝั่งขวา: กราฟเส้นอัตราความเร็วเมื่อเพิ่ม GPU เป็น 1, 2, 4 ใบ วางเส้นอุดมคติ `1×/2×/4×` บาง ๆ เพื่อให้เห็นว่าใกล้เส้นนั้น
- ใต้ตารางเวลา C2: แถบขั้นตอนสั้น ๆ `ภาพ → tensor/GPU → generate → decode/parse` พร้อมวงเล็บกำกับว่าเวลารวมเฉพาะ batch ที่สำเร็จหลัง warm-up

### คำพูดประกอบ

“การเพิ่ม batch บน A100 ทำให้ภาพต่อชั่วโมงเพิ่ม 3.82 เท่า ส่วนการแบ่งงานคงที่ 2,000 ภาพให้ 2 และ 4 GPU ลดเวลา inference ได้เกือบเป็นสัดส่วนกับจำนวน GPU ผล C2 นี้ใช้รอบ final หลังแก้ CPU contention”

ที่มาค่า C1: งาน 1,000 ภาพเท่ากัน ใช้เวลา pipeline มัธยฐาน `330.451 s` ที่ batch 1 และ `86.509 s` ที่ batch 8; จึงได้ `330.451 s ÷ 86.509 s = 3.82×` ซึ่งเท่ากับอัตราส่วน throughput เมื่อใช้ภาพเท่ากัน

ที่มาค่า C2: เวลา inference pipeline มัธยฐานที่ 1/2/4 GPU เท่ากับ `176.549 / 88.691 / 45.105 วินาที`; ดังนั้น `176.549 ÷ 88.691 = 1.991×` และ `176.549 ÷ 45.105 = 3.914×` เวลาของแต่ละรอบใช้ rank ที่ช้าที่สุด แล้วหาร efficiency ด้วยจำนวน GPU; C2 ยังไม่มี CI

หากถามว่าเวลานี้จับอะไร: โค้ดเริ่มจับเวลาต่อ batch ก่อนเปิดภาพ แล้วอ่าน/หมุนภาพตาม EXIF/แปลง RGB/ย่อภาพ, จัด prompt กับภาพเป็น tensor และส่งเข้า GPU, รัน `model.generate`, decode token และ parse คำตอบ ก่อนหยุดเวลา; `pipeline_seconds_total` รวมเฉพาะ batch ที่สำเร็จและไม่ใช่ warm-up ของแต่ละ rank ส่วน C2 เลือกเวลาของ rank ที่ช้าที่สุดต่อรอบ แล้วหามัธยฐาน 5 รอบ จึงไม่ใช่เวลาโหลดโมเดลหรือเวลาเสร็จงานทั้ง job

ไฟล์ผลมีเวลาโหลดโมเดล, generation, pipeline, และ complete-round wall แยกกัน; ยังไม่มีตัวจับเวลาแยกรายขั้นตอนสำหรับอ่านภาพ/เตรียม tensor/decode/parse จึงห้ามอธิบายว่าขั้นใดใช้เวลากี่วินาทีจากข้อมูลชุดนี้
